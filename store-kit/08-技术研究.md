## 议题一 · OVERLAPPED 热路径：风险定级为"真实但低概率"，正确修法已设计（继续挂起）

### 机制分析

`VddDriver.cs` 的 P/Invoke 签名是 `ref OVERLAPPED`（自定义 blittable 结构）。.NET 对 blittable 结构的 `ref` 传递采用**就地钉住**（不复制）：内核拿到的直接是托管栈上 OVERLAPPED 的地址。危险点在于：

1. 句柄以 `FILE_FLAG_OVERLAPPED` 打开 → IOCTL 排队为**异步 IRP**；
2. `DeviceIoControl` 返回（ERROR_IO_PENDING）→ **栈帧弹出，OVERLAPPED 内存失效**；
3. IRP 稍后在内核完成 → 内核向**已失效的栈地址**写回 `Internal/InternalHigh` 并 SetEvent → 踩栈。

### 为什么一直没炸

- Parsec VDD 的 UPDATE/ADD IOCTL 极轻量，内核大概率在 `DeviceIoControl` **调用内同步完成**（异步句柄不保证异步完成，驱动可同步完成 IRP）→ 写回发生在调用期间，内存有效；
- 心跳路径紧随其后同步 `GetOverlappedResultEx(1000ms)`，即使异步完成也在毫秒级内等到——等待期间栈帧仍在（`GetOverlappedResultEx` 与 `DeviceIoControl` 同帧）；
- 真正的踩栈窗口 = "DeviceIoControl 返回后、GetOverlappedResultEx 排队前，IRP 恰好完成"——纳秒级窗口 × 10 次/秒 ≈ 长期低概率。

### 正确修法（已设计，语义可论证、无需运行时验证编译层）

```csharp
// 1) P/Invoke 签名改为指针传递 (消除编组副本):
[DllImport("kernel32.dll", SetLastError = true)]
private static extern bool DeviceIoControl(IntPtr hDevice, uint ioControlCode,
    IntPtr lpInBuffer, int nInBufferSize, IntPtr lpOutBuffer, int nOutBufferSize,
    IntPtr lpBytesReturned, IntPtr lpOverlapped);          // 原为 ref OVERLAPPED

// 2) 心跳路径: 句柄存活期间常驻的原生 OVERLAPPED (AllocHGlobal 32 字节 + 预置 hEvent),
//    在 OpenHandle 成功时分配、CloseHandle 时释放 —— 内存生命周期严格覆盖 IRP 生命周期;
// 3) IoControl 通用路径: 每次 AllocHGlobal 分配 OVERLAPPED, GetOverlappedResultEx 之后 FreeHGlobal
//    (与现状的 try/finally 结构一致, 仅把"编组临时副本"换成"显式原生内存");
// 4) GetOverlappedResultEx / CancelIoEx 签名同步改为 IntPtr。
```

**可验证性**：编译期签名检查 + --selftest 全过 + 挂机 24 小时 + 夜间/本机切换 20 次。**实施条件**：你需要方便重启验证的时候。补丁代码保留在本文件，随时可应用。

### 决策

**继续挂起**。理由：现状已稳定运行数月（你日常使用即验证），而变更后若无验证就上线，引入回归的代价（远控断连）大于消除一个纳秒级窗口的收益。

## 议题二 · "开机后打开应用黑屏 20 秒"的深层机制：Windows 会回放显示器组合的记忆布局

### 机制链（完整版）

1. 旧版（≤1.0.0.0）启动**无条件预建**虚拟屏 → Windows 检测到新显示器加入；
2. **Windows 对每个显示器组合记忆最近一次布局**。你的历史布局中存在"虚拟屏为主屏 + 内屏熄灭"（息屏远控状态）——Windows 把它记在该组合名下；
3. 新屏加入时 Windows **回放记忆布局** → 桌面交给虚拟屏 → 内屏熄灭（黑屏开始）；
4. t=20s 首次巡检：本机模式 = 清掉所有虚拟屏 → 拓扑回退 → 内屏点亮（黑屏结束）。

"约 20 秒" = 首次巡检的固定 20 秒延迟（GuardianService.cs:174），创建发生在 t≈2-5s——**黑屏窗口 ≈ 5s~20s+，与你的体感精确吻合**。这不是偶发，是两条确定性机制的叠加。

### 社区佐证

- [VirtualDrivers/Virtual-Display-Driver Issue #31](https://github.com/VirtualDrivers/Virtual-Display-Driver/issues/31)：虚拟屏"自封主屏"是同类 VDD 的通病（重启/添加后抢占主屏），通用解即程序化重申拓扑（MonitorSwitcher 类工具）；
- [Tom's Hardware 讨论](https://forums.tomshardware.com/threads/preventing-a-specific-monitor-from-becoming-the-primary-display-in-multi-monitor-setup.3810955)：Windows 按精确组合记忆主屏设置。

### QuietScreen 的现状覆盖

| 场景 | 1.0.3.0 行为 | 覆盖 |
| --- | --- | --- |
| 本机打开（内屏活跃） | 不预建、不切拓扑 → 不触发记忆回放 | ✅ 黑屏根因消除 |
| 息屏远控中重启应用 | 全虚拟屏活跃 → 恢复夜间模式，不删屏 | ✅ 远端续命 |
| 夜间模式进入（需新建虚拟屏） | 创建 → 回放记忆布局（可能闪黑）→ SetNight 的 SwitchTo(ExternalOnly) 重申目标拓扑 | ✅ 闪黑属预期（本就要熄屏），且有守护收尾 |
| 外接屏用户本机打开 | 不预建、不切拓扑 | ✅ 既有设计保留 |

**结论：无需进一步增强。** 1.0.3.0 的"本机不预建"恰好绕开了记忆回放的触发条件（不添加新显示器就没有回放）。夜间模式的短暂闪黑是熄屏的预期表现。
